# 3.0.0 模块边界检查建议（草稿）

本记录仅为只读审查建议，不表示正式 3.0.0 宿主已实现。审查对象是当前 `source/` 单体程序、`modules/` 的资产清单，以及 `prototypes/module-packages/host-adapter/` 的独立 Android 应用安装验证壳。后者用于音乐等外置 APK 的安装、校验和启动，不是工具箱各栏目可卸载的完整宿主。

## 待办模块卸载后的权限入口

当前单体程序的全局权限页总是提供通知和准时提醒设置；待办、课程表、持续定位都可能使用通知，准时提醒又可能由课程提示使用。未来不能仅根据“待办是否安装”决定全部入口是否显示。建议各模块声明使用的系统能力，宿主按已安装且启用的能力合并显示权限入口；模块卸载后，先取消该模块自己的通知、闹钟、回调和开机调度，再移除仅属于它的设置。共享权限由其他模块继续使用时应保留入口。

当前 `todo/module.json` 的 `hostPermissions` 已声明通知、准时提醒及开机接收；仍须补充运行时能力注册与卸载清理契约。仅修改清单不代表完成权限隔离，也不能撤销整台设备或其他模块共享的权限。

## 底栏与模块安装状态

当前 `visibleTabs()` 和 `SettingsScreen.order("tab")` 基于固定栏目 ID，并保留显示开关，以确保单体版本至少显示一栏。未来宿主若以安装/卸载控制栏目是否存在，底栏设置应只对已安装、可用的模块排序，不应同时保留另一套易混淆的“隐藏即卸载”开关。停用、隐藏、卸载如均保留，必须分别定义数据保留及运行行为。

3.0.0 的默认安装列表已声明为 `weather`、`status`、`todo`；现有栏目 ID 不宜当作模块唯一身份，使用清单中的稳定字符串 ID。卸载当前模块时切换到明确可用的页面；允许全部工具卸载时须有宿主主页，而不是隐式恢复天气。

## 生命周期、数据和导航

各模块应拥有自己的视图、导航草稿、采样任务、持久数据及通知命名空间。宿主将“前台进入/离开”“模块停用”“卸载”“进程重建”分开通知；恢复导航不能自动获得定位、相机或通知权限，也不能把曾经采集过视为用户允许后台持续采集。

本次 2.2.1 修复的是桌面快捷方式 `CLEAR_TOP` 对标准启动模式造成的 Activity 重建：主入口改为 `singleTop`，新快捷方式另加 `SINGLE_TOP`。正常 Home 后返回可保留同一 Activity 的全部对话框和草稿。真实进程死亡后的任意编辑器恢复尚无通用契约；未来模块应显式保存可序列化草稿、稳定导航路径及滚动位置，不能长期保存旧 Activity、View 或闭包。

## 当前边界缺口

`ModuleRegistry` 的配置转移清单没有单独的 `weather-map` 项，但 `modules/modules.json` 已列出该模块；现有地图设置键保存在全局偏好中。未来应统一注册表和权限、配置清单，并为地图建立可独立转移的契约。当前单体栏目仍直接使用 `MainActivity` 的视图工厂与服务，不应将这些资产包描述为已能独立运行或安装。

音乐已经有独立 APK、模块 API 和外置安装适配，不应把音乐的独立 Android 应用安装机制与工具箱内部栏目卸载机制混为一谈。升级及卸载测试须分别覆盖两条路径。

## 已发布资产的实际内容

`modules/build_packages.py` 将 `SOURCE_SNAPSHOT` 固定为 2.1.5；每个栏目 ZIP 只有 `module.json`、配置契约、README 与 LICENSE，没有 DEX、资源、服务或广播实现。其清单正确声明 `standaloneInstallable: false`，但仍只是 metadata-only 规划资产，不是可安装、可卸载或可执行的完整应用。未来重新打包时应明确区分这类旧规划包与实际运行包，不能仅更改后缀或修改可安装标志。

`global` 被列为与工具并列的模块，却不在默认安装的三个 ID 中，且没有不可卸载标志。实际全局语言、权限、模块管理、完整配置及基础导航应留在不可卸载的宿主中；不能让卸载“全局设置”导致无法继续管理模块。用户可安装的完整应用内部仍可分为播放、曲库、分析等代码组件，它们不应要求用户分别安装。

## 资源、权限、服务与广播

当前 manifest 的定位前台服务、位置类型声明、通知权限和广播接收器均在单体宿主中。状态包的 `hostPermissions` 仅列位置和相机，没有描述前台服务及其位置类型能力；待办和课程表共享 `TodoReceiver`，其 `onReceive` 根据 `course.` 动作前缀转发，开机、时间和时区广播仍走宿主调度。未来必须由已启用模块注册能力和调度处理器，卸载时取消自身通知与 PendingIntent，并确保卸载后开机广播不会重新启动已移除模块。

模块资源应使用稳定资源命名空间和版本化接口；不能依赖旧宿主中的任意 `R.string`、私有 Activity 方法或其他应用类恰好存在。安装前验证权限、服务类型、依赖版本、入口、签名和内容哈希；卸载需停止传感器、相机、路线记录、前台服务及工作线程，再解绑资源和设置页面。删除数据应由明确的独立选项控制，不能误删共享文件或其他模块的通知。

## 配置转移的当前风险与建议

完整配置流程已有导入前校验、采集暂停、备份回滚和模型重建，适合用作未来宿主级迁移的基础；但固定 `ConfigurationData.GROUPS`、设置类型表及 `last_tab` 的数值 ID 仍假设所有模块存在。未来应先校验和暂存尚未安装模块的数据，不自动安装、启动采集或恢复权限；明确导入是否需要模块、是否保留未知模块资料及版本不兼容时的处理。

当前 `ModuleTransfer.confirm()` 删除旧值时使用 `ModuleRegistry.allowed()`，写入时却没有按同一模块边界再次筛选 `values.get(g)`。因此，将合法的其他全局键放进一个天文或地震模块文件，类型校验后仍可能写入同一 `toolbox` 偏好。多配置组的提交也没有完整回滚；完成后只 `refreshScreen()`，不会像完整配置导入那样重建全部模型，随机抽取等内存模型可能在下一次保存时覆盖刚导入的资料。它们是现有单体配置转移边界的风险，应另行修复和回归，不应将其直接照搬成未来模块安装器。

未来每个完整应用应提供版本化数据读写接口，由宿主检查所有权、范围和大小后原子提交；提供失败回滚、删除确认、卸载后保留及重装恢复测试。宿主范围的权限确认、运行状态和系统授权不进入可恢复配置。
