# 小球淘汰赛内部应用开发指南

## 项目状态与源码位置

小球淘汰赛仍是未来计划，当前不进入宿主桌面、应用商店、默认安装列表或正式发布包。设计和原型源码的唯一长期保存位置为 `modules/prototypes/ball-elimination/`。跨对话协作以该目录中的文件及 Git 提交为准，不依赖聊天记录长期保留。

`.ddapp` 是由宿主源码构建、使用宿主信任签名的可执行应用包。长期开发期间应保留可重建的源码和测试，不把早期生成的 `.ddapp` 当作未来正式包。宿主版本、接口、签名和兼容下限可能变化，决定实装版本后再用当时宿主重新构建、签名、登记及验证。

## 用户需求边界

已确认的核心玩法是多个小球同时参加竞速，按抵达终点的先后显示结果。它是本地娱乐小游戏，不是博彩、抽奖或竞赛投注功能。

首轮实现优先完整完成一场竞速的开始、进行、结束和排名。暂停/继续、重新开始、参赛数量、赛道样式、观赛速度等可作为设置提案；没有明确纳入范围前，不要为这些扩展改宿主或新增复杂规则。名次应基于越过终点的模拟时刻，平局处理须确定、可复现并在界面上说清楚。

所有比赛和设置在本机运行。不接入账号、广告、统计、网络服务、真实金钱或外部内容。游戏不需要定位、相机、蓝牙、通知等权限，不新增第三方依赖；如确有必要，先确认许可并说明理由。

## 当前宿主的应用契约

- 稳定应用 ID 建议为 `ball-elimination`，用户显示名称使用“**小球淘汰赛**”；英语显示名及界面文字也要一并准备。应用 ID 一旦进入正式目录就不可因改名而变化。
- 当前内部应用接口是 `daidai-toolbox/api-1`。接口名独立于工具箱显示版本。最低宿主版本、应用包版本和 Android 最低版本须在正式接入时按目标宿主重新确定，不要在原型中写死当前版本号。
- 可执行应用入口由宿主反射加载，入口须符合当前 `ModulePage` 契约并提供宿主要求的构造函数和生命周期处理。应用内普通返回、顶部返回和回到桌面的行为遵循当前内部应用宿主，不自行创建第二套桌面或商店入口。
- 应用包不是独立 Android APK，也不是只含说明文件的 metadata 包。宿主会校验签名、应用 ID、入口、接口、最低版本和包完整性。所有内部应用共用宿主 UID 与权限，不能把它描述成第三方代码沙箱。
- 全局配色、按钮样式、文字资源、桌面返回入口及应用资料规则遵循当前 `docs/MODULE-HOST.md` 和 `docs/DEVELOPER-RULES.md`。新增界面文字使用中文与英语资源，不在代码中硬编码可见文案。

## 原型目录约定

设计对话只在 `modules/prototypes/ball-elimination/` 下新增或修改小球游戏原型、设计资料和专属测试。建议按职责分开竞速模型、赛道绘制和宿主页面，避免把模拟逻辑、动画时钟和 UI 状态写成一个难以测试的类。目录中的源码暂不参与常规宿主构建。

当前工作区另有草稿 `modules/embedded/ballrace/org/daidai/modules/ballrace/RaceCourse.java`。`build.py` 会编译 `modules/embedded/` 下的源码，而现有执行包构建器没有登记 `ballrace`，所以该位置不适合作为长期原型目录。设计对话继续编码前，应先核对这个草稿并保留其内容，迁移到上述预留目录；确认迁移完整且有测试后，再清理旧位置。不要覆盖或丢弃这份已有草稿。

不要为了让原型暂时出现在应用商店而修改 `AppModules`、宿主入口白名单、`modules/build_executable.py`、商店目录、桌面图标注册、应用配置转移或当前 11 个应用。不要改动 `modules/host-java-api.json`、稳定资源编号或现有应用源码。若原型发现缺少宿主 API，记录最小需求和调用场景，留待宿主集成时评估；不得私自破坏或扩大 `api-1`。

不要把签名密钥、密码、SDK、构建缓存、模拟器数据或临时生成的签名包提交进 Git。发布时使用的密钥不得通过聊天、源码或测试资产传递。原型分支应提交源码、测试和说明，写明提交 SHA，便于多年后按提交取回。

## 竞速实现要求

竞速模型应与 Android View 分离，能够脱离界面测试球的位置、速度、赛道边界、终点判定、名次和暂停/继续状态。仿真按经过时间推进，不根据某一设备的绘制帧数决定比赛进度。若采用随机参数，应使用可注入的随机源，测试中固定种子，使比赛和排名问题可重现；不要让列表顺序或绘制顺序给某个小球固定优势。

赛道绘制使用自定义 View/Canvas 或当前仓库认可的绘制方式。绘制回调只负责绘制，不在 `onDraw` 内推进整场比赛、等待或执行文件/网络操作。动画仅在界面可见且生命周期允许时运行；离开、暂停、重建或销毁时停止回调，恢复后不重复计时、不泄漏 Activity。球数增加时避免逐帧创建大量对象，并在手机和平板尺寸、窄屏、文字缩放下检查小球和排名可读性。

越过终点的时间作为排序依据，名次稳定且结果不会因慢设备、掉帧或屏幕重绘变化。结束、暂停、继续和重赛只能改变一次对应状态；快速连续点击、旋转/重建、退到桌面后返回及后台切换不得导致多场动画同时运行或结果重复写入。

## 必须覆盖的测试

- 模型检查零个、一个和多个参赛小球，以及边界位置、终点判定、同一时刻完赛、平局规则和完整排名。
- 使用固定随机种子复测相同比赛；更换种子可以产生其他赛局，任何球都不因初始化或迭代顺序获得隐含优势。
- 检查暂停后比赛时间停止，继续后只推进一次；结束后不会继续更新，重赛会清空上一场结果。
- 检查界面退出、返回桌面、系统重建和多次点击后的动画回调清理及状态一致性。
- 检查中文/英语资源、全局颜色、按钮留白、桌面返回、横竖窗口尺寸和高文字缩放下的布局。
- 正式集成后，以目标宿主安装包完成应用安装、首次启动、再次打开、更新、卸载和资料保留测试，并运行宿主全套核心测试与 Android 双语交互测试。只通过编译不能代替界面和行为验收。

原型阶段的测试应能在设计分支上重复运行。原型不在主宿主构建路径内，当前宿主构建或测试不覆盖原型，报告中须明确这一区别。测试命令、运行环境和结果写在原型 README，不得把未运行的测试标成通过。

## 以后接入宿主和生成正式 `.ddapp`

用户决定进入某个工具箱版本时，先检查当时的 `AGENTS.md`、完整开发者准则、`docs/MODULE-HOST.md`、宿主 API 契约及 Git 状态。确认小球原型分支和提交 SHA，再把已验收源码移入当时采用的完整应用源码结构。不能只把原型包复制进商店，也不能沿用过期 `.ddapp` 的宿主版本和签名。

接入时至少逐项核对：

1. 为稳定 ID 注册执行入口、页面和宿主兼容信息，确认代码进入应用 DEX 而没有混入宿主 DEX。
2. 注册应用目录条目、中英文名称与说明、图标、版本更新说明、安装包 URL/哈希及商店展示信息。除非用户另行要求，不自动加入新装默认应用。
3. 仅添加实际需要的资源和配置契约；没有长期设置或个人资料时，不虚构配置分组。若保存战绩或自定义内容，定义版本化格式、损坏回退及单应用/全局备份导入导出行为。
4. 新增或改变宿主 Java/资源接口时保持既有 `api-1` 包兼容；无法兼容时另行升级接口版本并安排宿主更新，不将接口升级藏在应用包里。
5. 使用正式宿主构建脚本生成宿主 APK 和全部应发布 `.ddapp`，用原信任签名，核对包版本不高于宿主、最低宿主/Android 版本、目录元数据、SHA-256 和安装启动结果。
6. 更新桌面图标资源、商店目录、版本说明、开发者准则要求涉及的文档及验证记录。发布只在用户安排该版本时进行，且按正式发布流程验收。

当前关键实现入口可从 `docs/MODULE-HOST.md` 开始核对。构建器目前显式枚举已有应用，因此新增应用时必须同时调整宿主运行时注册、构建来源和商店目录。具体文件会随宿主版本变化，接入时以当时源码为准，不照抄旧版本清单。

## 给设计对话的启动指令

先阅读本指南、`modules/prototypes/ball-elimination/README.md`、`docs/MODULE-HOST.md`、`docs/DEVELOPER-RULES.md` 和仓库 `AGENTS.md`。先检查 `modules/embedded/ballrace/` 中已有赛道草稿，保留并迁移有用实现到原型目录，再继续开发。随后仅在 `modules/prototypes/ball-elimination/` 完成小球淘汰赛设计与原型代码、模型测试及中英文资源。维持其为尚未注册、尚未发布的内部应用原型，不修改宿主注册、现有应用、API、商店和发布文件。结束时列出文件、测试实际结果、未验证项和 Git 提交 SHA，供以后宿主集成对话取用。
