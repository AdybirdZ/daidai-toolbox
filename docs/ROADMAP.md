# 后续功能规划

以下项目的交付版本待定。

## 3.1.0 设备通信扩展

计划大幅提高可发送消息的容量，支持多设备通信和文件传输。目前仍是一对一文字通信，单条消息最多 4096 个 UTF-8 字节，最近 100 条会话消息仅在运行服务内存中保留。更大容量、多设备和文件传输均未实现。

扩大消息容量需重新确定协议版本、兼容协商、总量上限和内存预算，采用分块与流式处理，提供进度、取消、超时和失败反馈。保持对消息数量及累计字节数的约束，不以无限保留全部内容换取容量提升。

多设备通信需明确连接数量、对端身份、私聊或群组范围，以及消息接收者；不得默认把从一个对端收到的内容转发给其他设备。连接管理、权限撤销、密钥隔离和后台行为须单独验收。

文件传输需由接收方选择接受与保存位置，显示文件名、类型、大小和来源，校验剩余空间与文件完整性。限制单文件、总大小及并发数，防止越界路径和同名覆盖；取消清理未完成的临时文件，不删除源文件。收到文件不自动打开、安装或执行，也不自动作为指令处理。

蓝牙与局域网实现应共用明确的用户操作语义，同时分别验证真实设备、断连恢复和厂商后台限制，不承诺绕过系统强制停止。以上功能进入开发后，另行制定协议说明、双语界面文案及测试清单。

## 3.2.0 中文指令控制

从 3.2.0 起逐步提供以 `/` 开头的中文指令，用明确的应用名称、动作和参数调用工具箱功能。普通聊天文字不作为指令；不依赖猜测用户意图自动执行操作。可在后续设计中提供英语等语言的等价写法，但稳定应用身份和动作含义须一致。

按版本逐步开放，每次更新仅新增或完善一个应用的指令，完成解析、权限、资料校验和回归后，再进入下一应用；不在一次更新中为全部应用同时接入。可优先从待办事项开始。

每次只执行一条指令，且只面向一个应用。不得在同一输入中串联多个应用、用换行或分隔符拼接操作，也不支持脚本、循环、管道或任意代码执行。参数值中的普通标点与指令分隔须有明确语法，不能靠拆分用户正文猜测。

拟议结构为 `/应用 动作 参数名=参数值`，例如 `/天气 查询 地区="苏州市"`。此示例仅用于说明结构，目前不能输入执行，最终可用指令以实装时发布的手册为准。

实施时必须同时提供完整的用户语法手册，覆盖全部已开放的指令，不只列几个示例。每条指令须说明：

- 适用应用、动作及其实际结果，是否需要安装应用、联网或获得系统权限。
- 每个参数的名称、类型、单位、允许范围、必填或可选、默认值；无默认值时明确说明。
- 空格、引号、转义、空值、中文标点、大小写和重复参数的处理规则。
- 最小可用示例、包含可选参数的完整示例，以及易混淆输入的区别。
- 缺少参数、类型错误、超出范围、未知指令、应用未安装、权限不足等错误和处理方法。
- 是否读取或修改用户资料、是否产生通知、何时需要确认、成功与失败如何反馈。

解析须先完整校验，再请求执行；未知参数、歧义、额外指令和超限输入均明确拒绝，不默默忽略。输入长度、参数数量、单个参数长度、嵌套层级、解析时间和执行频率均设定有限上限，并在手册中公开；不得把增大普通消息容量等同于取消指令解析上限。

## 3.3.0 可信设备远程指令

计划允许用户选择是否接收指令，以及是否对带约定前缀的消息执行操作。接收入口和自动执行均默认关闭；收到普通消息、安装应用、导入配置或建立新连接时，不得自动启用。仅限用户明确配对并授权的可信设备；高影响操作仍须在接收设备上确认。

启用后只接受用户明确授权的可信对端，并可按应用或动作限定允许范围。可信身份须绑定经验证的对端身份；不能仅凭显示名称、IP 地址、蓝牙地址、消息文字或一个可复制的前缀认定可信。前缀只是区分消息类型，不能代替身份验证和授权。

指令执行前显示来源和完整操作含义；删除、覆盖、发送资料、文件操作及其他高影响动作必须在接收设备上确认。即使开启自动执行，也不能绕过此类确认或系统权限；锁屏及后台无法完成确认时应等待用户处理或拒绝执行。用户可随时撤销对端信任、关闭指令接收和自动执行。

实现时还需校验指令版本、消息身份和有效性，限制重复执行和执行频率；超长、格式错误、重复、过期或未经授权的指令不执行。反馈区分已接收、待确认、已执行和失败，不能把收到消息当作执行成功。记录与通知避免泄露配对凭据或完整敏感参数。

## 小球竞赛

多球竞速、参赛设置、排行榜、球外观编辑、可编辑关卡（含圆球、斜坡、圆弧和文字）、关卡导入导出及本地隔离测试宿主已在原型中实现。下列项目仍是计划，尚未进入游戏。

### 障碍物属性与行为（编辑数据已支持，运行行为待验证）

障碍编辑数据已加入圆形、椭圆、斜坡和圆弧，以及颜色、显隐、弹性、摩擦、碰撞开关、周期移动、绕轴旋转、附加冲量和定点传送字段。编辑数据格式为 schema 3，旧 schema 1 和 2 使用默认值兼容载入。运行时的动态碰撞、旋转障碍接触、传送冷却及大量动态障碍性能仍需接入或验证；完成前不视为可供玩家使用的完整功能。

### 关卡之间的连接通道

为每个关卡的入口和出口增加可编辑宽度。生成下一关时，只处理关卡边缘之间的连接区；玩家在关卡内部制作的漏斗和引导结构由玩家负责。连接区在两侧形成连续通道壁，不能留下小球可穿出的侧缝。连接斜率在安全范围内随机生成，开口的水平偏移与连接距离共同决定两端高度差。

通道最窄处须大于本场可能出现的最大球直径并保留碰撞余量。通道设计依赖未来变半径区域的尺寸上限；在该上限明确前，不把当前默认小球半径当作永久尺寸。先支持上下方向，再按同一连接规则扩展到左右及其他方向，并检查通道不越界、不自交、与开口正确衔接。

### 小球尺寸变化区域

在关卡编辑器中新增可放置、选中、修改和删除的尺寸变化区域。区域至少需要位置与覆盖范围、触发形状、目标半径及合法半径上下限；还要明确变化是立即生效还是平滑过渡，以及小球离开后保持新尺寸还是恢复。触发需避免小球停留在区域内时重复重置尺寸。

实现时同步更新小球的碰撞半径、质量和转动惯量，并确定与其他小球、障碍物及终点重叠时的处理。保存格式需兼容既有关卡；比赛设置、排行榜和绘制均使用运行时半径。完成尺寸变化后，关卡连接通道按本场可能达到的最大半径验证通行空间。

建议顺序：先实现尺寸区域的数据格式、编辑交互和物理测试，再确定可达最大半径；随后实现关卡间通道生成、随机斜率范围及多方向连接测试。安全边界、最窄宽度、最大球半径和随机范围通过测试后再交付设备验收。

原型源码和本地隔离测试宿主保存在 `modules/prototypes/ball-race/`，不参与正式宿主构建或商店发布。内部应用接口、测试构建和未来接入边界见[小球竞赛本地测试宿主指南](BALL-RACE-DDAPP.md)。正式接入时须按目标宿主重新构建签名包。
